# テスト戦略とリスク対策

[English](../04-testing.md) | 日本語

本書は tasuki のテスト戦略、検証方針、および設計上のリスクと対策を定める。
組み込み型 durable workflow エンジンとして、tasuki はプロセスのクラッシュ、ネットワークの切断、データベースの並行競合が発生しても、exactly-once の状態遷移とデータ整合性を保証する必要がある。

## 検証方針と原則

- **プロトコル検証の優先**: 正しさの中核である状態遷移プロトコル、並行性制御、およびリース機構は、共通のバックエンド適合テストスイート（`backendtest`）としてコード化する。すべてのバックエンド実装は、この同一のテストスイートによって同じ不変条件を検証される。
- **カオスと耐障害性の実証**: 正常系だけでなく、プロセスの突然の強制終了（`kill -9`）やデータベースの競合など、過酷な障害条件下でも正しさが損なわれないことをカオステストで実証する。
- **実行可能なドキュメントテスト**: ドキュメントやコード例が本体の進化から乖離（ドリフト）しないよう、ドキュメントに記載された API やワークフロー例は CI 上で自動テストとしてコンパイル・実行される。

## テスト戦略

| 層 | 焦点 | スコープと検証手法 |
|---|---|---|
| **単体・リプレイ** | ゴールデンテストと決定論検証 | 記録済みジャーナルに対してワークフロー関数を再生し、完全に同一のコマンド列が生成されることを検証する。仮想時計（`wftest`）を用いて、スリープテスト等を実時間待ちなしに瞬時に検証する。 |
| **適合スイート** | バックエンド実装契約の共通検証 | 全対応ストアに共通する永続化契約を検証する。タスク獲得の排他、リース失効後の再獲得、タスク削除と ensure の並行競合による起こし損ね防止（不変条件 I1）、`next_seq` フェンシング、完了の二重実行防止、シグナル競合、Capabilities 予算管理などを網羅する。 |
| **カオス E2E** | クラッシュ復旧と永続性の実証 | 高負荷下で複数のワーカープロセスに対しランダムに `SIGKILL`（`kill -9`）を反復注入する。全インスタンスが最終的に整合した終端状態に達し、ジャーナルに遷移の重複や欠落・破損がないことを検証する。 |
| **常時検証** | レース検出とファジング | すべてのテストを Go の競合検出器（`-race`）を有効にして実行する。ペイロード Codec や合成リプレイ入力に対して継続的なファズテスト（`go test -fuzz=Fuzz ./codec ./internal/engine`）を実施する。 |
| **CI マトリクス** | 多環境での自動検証 | PostgreSQL、MySQL / MariaDB、Spanner（エミュレータ）、DynamoDB（DynamoDB Local）、Firestore（エミュレータ）のコンテナ／エミュレータ環境、および追加インフラ不要の SQLite、インメモリ環境を CI マトリクスで自動実行する。 |

### バックエンド適合テストスイート

適合テストスイート（`backendtest`）は、すべての永続化バックエンドが満たすべき統一仕様を定めている。新規にバックエンドを追加する場合でも、このテストスイートを変更することなく通過することが求められる。

検証される主要な不変条件：
1. **獲得の排他性**: リース中のタスクは、リース期限が切れるまで他のワーカーから重複して獲得されない。
2. **起こし損ねの不在（不変条件 I1）**: タスク完了・削除と inbox へのイベント投入が同時に発生しても、タスクの実行漏れや永久滞留が発生しない。
3. **楽観ロックによるフェンシング（`next_seq` CAS）**: 古いシーケンス番号に基づく前進処理はコンフリクトとして確実に拒絶される。
4. **二重完了・遅延完了の保護**: アクティビティ完了の二重送信や、ワークフロー終端後に遅れて到着した完了通知は安全に無視・拒絶される。
5. **Capabilities 予算管理**: `Capabilities.MaxAdvancementEffects` を宣言するストアにおいて、制限を超えるファンアウトが複数 tick に安全に分割コミットされる。

### カオスと耐障害性テスト

カオステストは、複数プロセス間でワークフローを分散実行しながら予期せぬクラッシュを擬似的に発生させ、現実世界の過酷な障害に耐えられるかを検証する：
- ワークフロー前進中やアクティビティ実行中に、ワーカープロセスを `SIGKILL` で即死させる。
- 残された別ワーカーが失効したリースを引き継ぎ、最新のジャーナル状態から安全にワークフローをリプレイ・再開する。
- 全体の終了後、ジャーナルイベントの欠落や重複がなく、全インスタンスが期待される計算結果で終端していることを検証する。

### 継続的インテグレーション

CI（`.github/workflows/ci.yml`）はプルリクエストと `main` への push ごとに実行し、さらに nightly スケジュール（UTC `0 3 * * *`、`workflow_dispatch` による手動実行も可）でも実行する：

| ジョブ | ゲート内容 |
|---|---|
| `lint` | root と backend に `staticcheck` が clean であること |
| `vuln` | root と backend への `govulncheck`（参考表示。stdlib の指摘は toolchain に追従するため非ブロッキング） |
| `root` | `go test ./... -race`。fuzz の seed は通常の単体テストとしてここで実行 |
| `backend-*` | backend ごとのスイートを `-race` 付きで実行 |
| `chaos-*` | `kill -9` カオスを `-race` 付きで実行（インフラ不要の `chaos-sqlite` を含む） |
| `cover` | root のカバレッジサマリと成果物 |
| `gowork-check` | `GOWORK=off` の独立性、workspace の `tasuki_all` ビルド、`go test -tags tasuki_all ./contrib/... ./examples/...` |
| `fuzz-nightly` | nightly のみ。各 codec/engine ファズ対象に `-fuzz -fuzztime` 60 秒 |

CI の Go は全ジョブで `1.24.x` を使用する（`docs/ja/10-modules.md` 参照）。

## リスクと対策

分散・耐久ワークフロー実行において想定される技術的リスクと、tasuki のアーキテクチャによる対策は以下の通りである：

| リスク | 影響 | アーキテクチャ上の対策 |
|---|---|---|
| **決定性制約の踏み外し** | インスタンスが `stuck` 状態に隔離される | `*workflow.Context` の型による構造的防止、非決定性呼び出し（`time.Now`、`go`、`rand` 等）を検出する静的解析器、および実行時照合と手動リトライ機構の三段構え。 |
| **ジャーナルの肥大化** | リプレイ遅延とストアのストレージ圧迫 | 警告しきい値（`JournalWarnThreshold`）、インメモリのスティッキージャーナルキャッシュ、および `workflow.ContinueAsNew` による履歴リセット指針。 |
| **ホットインスタンス** | ターン直列化によるスループットの頭打ち | インスタンス単位でタスクが直列実行される特性に配慮し、子ワークフロー（`ExecuteChild`）への分割、キーによるシャーディング指針を提示。 |
| **プライマリ DB への負荷** | アプリケーション本体のクエリへの影響 | 接続設定による別 DB や別スキーマへの分離、`tasuki.tasks.backlog` メトリクスによる早期可視化、autovacuum チューニングガイド。 |
| **ストア固有セマンティクスの差**（ロック待機 vs CAS 中断等） | 移植時の起こし損ねや排他漏れ | 保証を不変条件（I1 等）として定式化し、全バックエンド実装を共通の適合テストスイートで均一に検証。 |
| **書き込み件数上限の制約**（DynamoDB、Firestore） | トランザクション操作上限の超過 | `Capabilities.MaxAdvancementEffects` で上限を宣言し、エンジンが許容予算内のプレフィックスのみをコミットして残りを次ターンに安全に繰り越す。 |
| **権威時計のないストア** | リース重複や余分な再実行の増加 | 正しさは CAS とタスク削除の排他で担保し時計のずれに依存させない。安全マージンを設定可能にする。 |
| **関数リネームによる非互換** | 実行中インスタンスのリプレイ失敗 | 明示的な登録名（`worker.WithName`）の利用を推奨・サポートする。 |
| **ペイロード構造の進化** | 古いジャーナルイベントのデコード失敗 | 追加のみを原則とするスキーマ進化ルールの明示、プラガブルな Codec による暗号化やバージョニング対応。 |
| **アクティビティの二重実行** | 外部システムでの副作用の不整合 | at-least-once 実行を契約として明示し、外部呼び出しの重複排除用キーとして安定した `IdempotencyKey` を提供する。 |
